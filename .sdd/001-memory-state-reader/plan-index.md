## 2. Goal

针对仓库自带的 32 位《植物大战僵尸》1.0.0.1051，先建立 Python 3.12.13 的只读内存采集工程，读取用户已验证的阳光与已知实体字段，并调查公开逆向资料给出的卡槽、场景、关卡、波次、地形和对象活性候选偏移。单帧可对照的值可带“待动态核验”标记展示；经过事件实测的字段标为可信，无法确认的字段标为未获取。本地浏览器以状态栏、卡牌区、5×9 棋盘和独立僵尸覆盖层展示 State。验证先读取用户已暂停且有僵尸的进程，检查一次采样及页面；动态部分由用户亲自玩一关并决定观察结论。001 只做观测，不调用 JEV，也不操作游戏。

## 3. Scope

### In scope

- P01 建立项目配置、`uv` 环境、`pywin32` 进程发现与 `ctypes` 只读内存模块；P02 读取已知字段并验证公开候选偏移；P03 构建带逐域可用性的 State；P04 提供本地 Web 状态监视器。
- 预期项目布局为 `runtime/` 负责通用 Windows 进程/内存能力，`configs/` 存目标版本身份和静态偏移，`game/` 解码 PvZ 原始数据，`state/` 归一化快照，`dashboard/` 提供只读页面；`main.py` 在根目录组织 `probe`/`snapshot`/`serve`。依赖只从展示层向下流动，`runtime/` 不导入上层目录。
- 目标文件 `.game/PlantsVsZombies.exe` 的 FileVersion 为 `1.0.0.1051`、PE Machine 为 `0x014C`、SHA-256 为 `F587903E9C3AD3890C1F4E2FBC1FE1EA88BD191E3D623D6F291283F6658C8DD4`。当前进程模块基址实测 `0x00400000`；用户给出的 `0x006A9EC0` 对应模块 RVA `0x002A9EC0`。
- 用户提供的 Board 链和阳光、数组指针/数量、结构步长及字段偏移记录在 P02。一次只读实测得 `Board=0x16F67D20`、阳光 100、植物数 1、僵尸数 0、掉落物数 0；这些进程内绝对地址仅作证据，不写死为运行配置。
- 用户已验证字段优先。公开逆向资料找到 `Board+0x144` 卡槽、`Board+0x5550` 关卡、`Board+0x168` 地形、`Root+0x7FC` 场景等候选；其证据与验证顺序列于 P02 和 `state-checklist.md`。候选若在暂停现场经画面/结构对照成功，可用 `provisional` 暴露读数并在页面标“待动态核验”；事件前后核对通过才标 `available`。无法确认的字段仍为 `unavailable`。
- 用户提供的 [暂停前画面](evidence/001-game-before-pause.png) 和 [暂停画面](evidence/002-game-paused.png) 是固定参照：截图中显示 1-3、阳光 3333、五行草坪、右侧一只僵尸、前一张有掉落阳光；暂停遮挡了部分植物/格子。它们不能证明日后采样仍是同一帧，也不能证明内存字段正确。第一部分验证须在当时仍运行的目标进程重新取样并记录时间、PID、身份、raw/State/API/UI 的对照；若该进程已退出，应由用户在 Verify 阶段重新提供暂停且有僵尸的现场，而不能用截图冒充内存证据。
- 第二部分验证仅在用户自行恢复/操作游戏并愿意观察时进行。自动采样和浏览器展示可运行，但工具/代理不发送鼠标键盘动作、不给游戏写内存，也不自行判定用户体验通过。
- 使用 Python 标准库提供 JSON 与本地 HTTP 页面；运行时第三方依赖仅 `pywin32`。`uv` 是开发环境工具，当前机器尚未安装。

## 7. Validation

1. P01：`uv run python --version` 必须为 3.12.13；`uv run python -c "import win32process, win32api"`；`uv run python main.py probe` 经过 `main.py → configs/ → runtime/` 只读核对目标。当前机器有 WinGet，但 `uv` 尚不可用；[uv 官方安装与 Python 管理文档](https://docs.astral.sh/uv/getting-started/installation/)支持所规划命令。
2. 第一部分（代理可执行的静态现场检查）：保持游戏暂停，执行 `uv run python main.py probe`、`uv run python main.py snapshot --once` 和 `uv run python main.py serve --port 8765`（若该端口已被占用则自行选择空闲端口）；记录同一次/相邻采样的时间、PID、程序哈希、原始值、State、`GET /api/state` 和页面截图。与现场游戏画面比对阳光、当前植物、至少一只僵尸的行/类型/位置、掉落物和卡槽等可见字段；截图中的 3333、1-3 与一只僵尸只是拍摄时的参照，不预设为本次采样值。暂停时重复采样应显示新采样时间，但不凭 CSS 动画制造实体运动。候选字段只能得到 `observed_once` 证据等级并以 `provisional` 状态显示；需要变化才能证明的语义仍待第二部分验证。端口冲突处理不列入验收。
3. 第二部分（用户操作和决定）：用户自行恢复并玩一关；采样器和页面持续只读运行。观察自然发生的阳光增减、种植/移除、卡牌冷却、僵尸移动/受伤/消失、掉落物、波次/阶段；若结束或重启发生则检查指针链与错误恢复。用户记录其观察和是否接受；代理将 raw/State/API/UI 证据关联到对应事件，不替用户操作或给出 human 通过结论。没发生的事件保留未验证，不强造测试场景。
4. 自动检查：`uv run python -m unittest discover -s tests`，并检查空列表、读失败、未映射、关闭进程和重新连接的语义。当前本地前置目标的通过条件是 R1–R8、R10–R13 的实现与必要证据、空闲端口页面/API 正常，以及用户本人对试玩效果作出判断；R9/R14 的严格联证和真实退出/恢复现场作为已知后续项记录，不阻止本次通过。不得将未观察的事件或恢复行为记为已验证。
5. 当前仓库没有应用 manifest、源码、测试或 CI；以上 `uv`/模块命令由各 Plan 实施后提供。方案结构用现有 `python .codex/hooks/check_iteration_names.py` 检查。

P02–P04 具体 Plan 中较严格的 R9/R14 追踪和手工检查仍保留为后续证据清单；其当前交付门槛以本 Index 的修订版 Requirement Baseline、Confirmed Decision 和第 4 条为准。

## 8. Risks

- 用户提供的偏移与本机样本只验证了 Board 链、阳光和部分容器字段；僵尸/掉落物实体以及 HP、X/Y 类型仍需活对象核对。
- 公开头文件将数组 `+0x4` 命名为“count”，而用户 `+0x10` 为当前数量；逆向 `DataArray` 结构显示前者是已用槽位上限，后者是活数。P02 必须在目标程序核实，不能复制含混名称。
- 卡牌费用可能由游戏逻辑动态计算，卡槽内未找到可直接读取的费用字段；001 若不能以当前关卡画面验证准确费用，State 与页面显示“费用未获取”。“不可种”也不能仅凭地形码或植物占用推定。
- 数组当前数量不等于槽位遍历上限，必须查清高水位与活性标记；否则会漏读或显示幽灵对象。
- `uv` 当前未安装，Python 3.12.13 也未安装；P01 的环境建立和 `pywin32` 下载依赖网络。用户已明确同意使用二者，具体安装结果仍需验证。
- 四个 Plan 超过小改动基线，因为仓库没有应用工程且用户新增动态可视化；各层按可独立验收的项目基础、原始读取、State、浏览器显示拆分。
- 当前暂停进程是易失的现场，Implementation/Verify 到来时可能已退出或换帧；归档截图只用于说明预期画面，第一部分必须重新取现场证据。第二部分取决于用户何时玩这一关；等待期间不可擅自补齐动态验证结论。
