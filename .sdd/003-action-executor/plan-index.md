## 2. Goal

为后续 JEV 调用提供三个受 State 约束的游戏 UI 动作：放置植物、点击收取掉落物、对格子执行一次原生铲除。调用者提交卡槽、行列或 item ID 等语义参数；执行器将客户区坐标对应的鼠标消息直接投递给已校验的目标 HWND，不要求游戏处于前台，并以动作前后的 State 确认结果。本次唯一 G1 验收顺序为按卡槽 1–10 循环种满 5×9 草坪、逐格铲除至全空、再以 5 秒间隔动态收集掉落物并核对阳光增量。Human 负责配置游戏在后台继续运行、不暂停并冻结僵尸；由于 Human 已修改游戏数据消除冷却，本次动作不等待或检查卡槽冷却。

## 3. Scope

### In scope

- 单一 P01：固定目标窗口上的三类语义动作、JSON CLI、State 确认及一次 Human 实机验收。
- 使用现有只读进程身份和 State 采样；卡槽/草坪/铲子点击依据目标 HWND 客户区及版本配置计算，收取点击依据当前 State 的 item ID 与坐标计算，并用目标 HWND 定向消息支持后台交互。
- Human 在 PvZ 后台持续运行、不暂停且僵尸冻结的设置下执行唯一 G1 流程：按 0 基行列行优先遍历 45 格，卡槽 1–10 循环，不检查或等待卡槽冷却；每次放置等待目标格 State 后置条件。随后重复按格铲除，直至所有格为空。最后记录阳光基线，每 5 秒采样并收取新出现且坐标可解析的掉落物，验证至少两个不同 ID 消失且阳光增量严格大于 25。
- 收集循环使用既有 `snapshot --once` 与单次 `collect_item` CLI 调用编排，不新增常驻收集服务或 batch API；达到至少两个不同 item ID 消失且同 PID 阳光增量 >25 时结束。未达目标的最大总时长见 P01 的 OD-06。
- 仅做执行者与语义动作，不增加依赖。

### Out of scope

- JEV/LLM 决策和自动单僵尸通关。
- 自动选择植物、判断“哪种植物适合哪格”、阳光余额/费用检查；人工准备可在当前草坪使用的十张卡并提供充足阳光。
- 自动修改游戏运行参数、暂停状态、僵尸状态或其他内存；这些由 Human 在 V01 前准备，执行器仍只读进程内存并投递窗口消息。
- 按植物 ID 精确选层、支持所有 item 类型、其他游戏版本及窗口布局。
- 将替身测试或模拟输入设为实机 Human 验收之前的独立通过层。

## 8. Risks

- `PostMessageW` 返回成功只表示消息入队，不保证游戏已处理；每次客户区鼠标消息均定向至重新校验的 PID/HWND，仍须依靠同 PID State 后置条件确认。不同完整性级别可能触发 UIPI 拒绝；窗口队列不处理后台消息时，动作必须保持 `unverified`，不得重试。
- 草坪首格 x 坐标按实机行为校准：`x=120` 曾实际落入 `(0,1)`，现用 `x=80`；其他格位及其余两个动作仍需在 V01 中验证。
- 45 次放置与后续清理需要等待 State 更新；卡槽冷却按 Human 修改后的无冷却游戏状态忽略。每步 State 等待必须有界；超时为 unverified，不自动重试。
- item 坐标当前是 candidate/provisional；仅有限、可解析且落在当前支持客户区范围内时允许实测，保留原始 evidence；null、歧义、无法解释或越界时拒绝。
- 当前 State 的植物 ID 变化可能受同时发生的其他操作影响；同一 PID、逐步操作和 before/after 样本用于降低归因歧义。
- 卡槽预先由 Human 准备；程序不判断阳光、卡费或某种植物适合哪个格子。未知植物可种性由实机结果确认。
- 阳光余额与 item 字段仍为 provisional/candidate；V01 必须保留阳光基线、收集后的余额和每个 item ID 的 State 变化。读数未变化或增量未严格大于 25 时不通过收集验收。
- 5 秒动态收集最长 120 秒；若阳光余额无法读取、增量未超过 25 或收集不足两个不同 ID，记录失败及现有证据。
