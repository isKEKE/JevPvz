# JEV 玩植物大战僵尸：能做什么，卡在哪里

> 2026-09-28 整理。实测用的是 `jev-1.13.0`。这是对 JevPvz 这套系统的复盘，不是给 JEV 模型判一个永远不变的上限。

一开始，我想的事情很直接：把游戏状态读出来，让 JEV 选动作，再把动作送回游戏。听起来像一条很短的链：`State → JEV → Action`。真跑起来才发现，“下一株种什么、种在哪一行哪一列”根本不是一个问题。要看阳光够不够、哪行快守不住了、哪行已经有火力、植物以后会不会挡住阵型，还要考虑一株向日葵现在花掉阳光，回报却在几十秒以后。

这次实验让我看到两件事：**JEV 确实能在真实游戏里连续做决定；但它做得了下一步的选择，不代表这些选择会自然拼成一套长期策略。**

## 五局游戏，实际跑出了什么

这五局由人实际运行并标注胜负，日志记录了 JEV 的请求、选择、动作和游戏结束状态。完整核对在 [006 验证记录](../.sdd/006-jev-runtime-loop/verify.md)。

| 日志 | 当时的状态 | 跑到哪里 |
| --- | --- | --- |
| [01](../.log/test_01.jsonl) | 没加经验 | 到 wave 14，未取得 1-1 通关证据 |
| [02](../.log/test_02.jsonl) | 刚加经验 | 到 wave 10，未取得 1-1 通关证据 |
| [03](../.log/test_03.jsonl) | 迭代了经验 | Human 确认通过 1-1 |

通过 1-1 和 1-2 不是纸上模拟：JEV 真的参与了选择，系统真的在游戏里种植、收集并推进关卡。这是这次实验已经做到的事。不过，通关的是**JEV 加上整套 Harness**：游戏内存读取、植物目录、合法候选、经验文本、动作校验、调度和结果确认都在帮它完成任务。

## 为什么通关之后，我仍然觉得策略不够稳

早期最明显的一幕在 [01 局的 `event_sequence=312–320`](../.log/test_01.jsonl)：第 0 行已经有五株资源植物，其他行还没有，JEV 仍选了 `sunflower@r0c6`，而且真的种成功了。它选的格子是合法的，但资源继续堆在同一行，并不等于整个草坪更好守。

后来，我们已经把行威胁、植物角色和布局经验送进请求，问题也没有完全消失。[05 局的 `event_sequence=568–571`](../.log/test_05.jsonl)里，第 2、3、4 行有僵尸却没有攻击植物，都是 `undefended`；第 0 行没有僵尸。JEV 仍选择并成功在第 0 行种豌豆射手。提前种远程植物有道理，但这一次它压过了眼前几行的防守缺口。这正是我说的“需要跨行比较优先级”，而不是再添一个标签就能彻底解决。

经验也不是硬规则。[05 局的 `event_sequence=2636–2651`](../.log/test_05.jsonl)中，第 4 行已有两株资源植物，JEV 又在第 4 列种了一株向日葵，偏离了“资源植物宜放第 0、1 列”的[经验文本](../configs/plant_experience.txt)。单凭这一株不能断言整局因此变差；它说明的是，提示模型一种布局偏好，不等于模型每一步都会稳定照办。

话也不能说成“JEV 完全不会停”。05 局的 plant 请求有 92 次选择种植，也有 140 次选择等待。系统给了它 `none_of_the_above` 这个弃选项。真正难的是判断：这一行是否已经够强？现在多种一株，是否比补另一行或存下阳光更值？

还得把**策略选错**和**系统没有把选择执行出来**分开看。01、02 局有 109、188 次可点击的阳光落在错误配置的区域外；修好后，03–05 局这类记录是零。04 局还有 753 条收集批次被新批次覆盖的记录；改了队列后，05 局这类记录也是零。[验证记录](../.sdd/006-jev-runtime-loop/verify.md)列出了计算口径。这些是 Harness 的观察和执行问题，不能怪到 JEV 的植物策略上。

## 官方其实怎么描述 JEV

TypeSafe 把 JEV 叫作 **System One**：它接收 State，回答预先定义好的问题，返回类型化的选择和概率；目前不直接看图像。官方强调的是快速、聚焦的判断，而不是让它独自完成一整段慢速规划。[System One](https://docs.typesafe.ai/concepts/system-one)。官方也建议把复杂判断拆成小问题，把能精确算的东西留给代码，再由代码组合答案。[Primitives](https://docs.typesafe.ai/primitives)。

这和我们踩到的坑很接近。TypeSafe 自己列出的 `jev-1.13` 弱点包括计数、数字精度、多层间接推断、无关信息过多和互相冲突的说明。[Jev 1.13 jaggedness](https://docs.typesafe.ai/model-jaggedness/jev-1.13)。所以，“给 JEV 更多 State”不能简单理解成把所有游戏数据一股脑塞进去。更有用的是算好相关事实，讲清楚问题，让它判断它真正擅长的不确定部分。

官方提到的低幻觉也要说准：**输出被限制在给定的类型和候选里**，它不会凭空返回一株候选里没有的植物。这保证接口容易接，不保证它在合法候选里选的是最好的行和格子。[Primitives](https://docs.typesafe.ai/primitives)。官方的 Doom 演示同样使用结构化 State，并明确说传统 bot 可能打得更好；一个实时游戏演示不能直接回答 PvZ 的资源经营问题。[官方发布文章](https://typesafe.ai/blog/introducing-system-one-models-and-jev)。

## 我现在怎么看它在 Harness 里的位置

我更愿意把 JEV 看成一个**反应快、输出可靠的判断部件**。代码负责读状态、算数量和距离、筛合法动作、确认有没有执行；JEV 负责某些难以写死、但能问得很具体的判断，例如“眼前哪一个合法方案更合适”。这不是要把策略机械地拆成五次 JEV 请求。官方说明，同一份 State 上的独立问题可以放在一次请求里；只有后一个问题必须等前一个答案才能构造时，才需要再请求。[Primitives](https://docs.typesafe.ai/primitives)。

JEV 每次拿到新 State 都能改变下一步选择，所以它不是对局面毫无反应。但**响应新局面**和**从一局成败中总结、检验、保存新经验**是两回事。当前十条经验是人写入文件的；这套系统还没有自动复盘和跨局更新的闭环。这个缺口属于当前 Harness，不能直接写成“模型天生永远学不会”。

如果将来真要继续完善，一个合理的方向是按时间尺度分工：快速环节继续由代码和 JEV 处理局部变化；每到新波次或重大失误，调用 LLM/Agent，结合当前局面思考下一段时间的资源目标、行优先级与预留阳光；局后再检查这些建议是否有效，只有验证过的经验才带入下一局。长期计划还需要能过期，免得旧目标挡住眼前的紧急防守。这是**后续设想**，五局实验没有实现或验证它。接入 LLM/Agent 后，新增的规划能力属于整套 Harness，不应算成 JEV 单独拥有的能力。

## 最后怎么下结论

这次至少证明了一件实在的事：**在准备好 State、候选和执行闭环后，JEV 能参与真实游戏并帮助系统通过两个关卡。** 同时也看到了当前集成的边界：局部判断会做，但资源投入、跨行火力和空间布局仍可能互相打架。

我不会把五局游戏说成 JEV 的“理论上限”。配置每局都在变，没有固定规则或其他模型作同条件对照，也没有把模型、经验和 Harness 的贡献单独测出来。更准确的说法是：**JEV 让 Harness 拥有了一个很有用的快速判断节点；要让整套系统越玩越会玩，规划、记忆、复盘和可靠执行仍要另外建设。**
