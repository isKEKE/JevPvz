# 从植物大战僵尸看 JEV 在 Harness 里的位置

> 2026-09-28 初稿，2026-10-04 更新。五局实测用的是 `jev-1.13.0`。这是一份 JevPvz 系统复盘，不是给 JEV 模型判一个永远不变的上限。

一开始，我想的事情很直接：把游戏状态读出来，让 JEV 选动作，再把动作送回游戏。听起来像一条很短的链：`State → JEV → Action`。真跑起来才发现，“下一株种什么、种在哪一行哪一列”根本不是一个问题。要看阳光够不够、哪行快守不住了、哪行已经有火力、植物以后会不会挡住阵型，还要考虑一株向日葵现在花掉阳光，回报却在几十秒以后。

这次实验让我看到两件事：**JEV 确实能在真实游戏里连续做决定；但它做得了下一步的选择，不代表这些选择会自然拼成一套长期策略。** 后来的测试又让我看到，整个系统的表现，还取决于 Harness 怎样安排状态、目标、候选、执行和反馈。

## 五局游戏，实际跑出了什么

这五局由人实际运行并标注胜负，日志记录了 JEV 的请求、选择、动作和游戏结束状态。完整核对在 [006 验证记录](../.sdd/006-jev-runtime-loop/verify.md)。

| 日志 | 当时的状态 | 跑到哪里 |
| --- | --- | --- |
| [01](../.log/test_01.jsonl) | 没加经验 | 到 wave 14，未取得 1-1 通关证据 |
| [02](../.log/test_02.jsonl) | 刚加经验 | 到 wave 10，未取得 1-1 通关证据 |
| [03](../.log/test_03.jsonl) | 迭代了经验 | Human 确认通过 1-1 |

通过 1-1 和 1-2 不是纸上模拟：JEV 真的参与了选择，系统真的在游戏里种植、收集并推进关卡。这是这次实验已经做到的事。不过，通关的是**JEV 加上整套 Harness**：游戏内存读取、植物目录、合法候选、经验文本、动作校验、调度和结果确认都在帮它完成任务。

## 为什么通关之后，我仍然觉得策略不够稳

早期最明显的一幕在 [01 局的 `event_sequence=312–320`](../.log/test_01.jsonl)：第 0 行已经有五株资源植物，其他行还没有，JEV 仍选了 `sunflower@r0c6`，而且真的种成功了。它选的格子是合法的，但资源继续堆在同一行，并不等于整个草坪更好守。

后来，我们已经把行威胁、植物角色和布局经验送进请求，问题也没有完全消失。[05 局的 `event_sequence=568–571`](../.log/test_05.jsonl)里，第 2、3、4 行有僵尸却没有攻击植物，都是 `undefended`；第 0 行没有僵尸。JEV 仍选择并成功在第 0 行种豌豆射手。提前种远程植物有道理，但这一次它压过了眼前几行的防守缺口。这正是我说的“需要跨行比较优先级”，而不是再添一个标签就能彻底解决。

经验也不是硬规则。[05 局的 `event_sequence=2636–2651`](../.log/test_05.jsonl)中，第 4 行已有两株资源植物，JEV 又在第 4 列种了一株向日葵，偏离了“资源植物宜放第 0、1 列”的[经验文本](../configs/plant_experience.txt)。单凭这一株不能断言整局因此变差；它说明的是，提示模型一种布局偏好，不等于模型每一步都会稳定照办。

话也不能说成“JEV 完全不会停”。05 局的 plant 请求有 92 次选择种植，也有 140 次选择等待。系统给了它 `none_of_the_above` 这个弃选项。真正难的是判断：这一行是否已经够强？现在多种一株，是否比补另一行或存下阳光更值？

还得把**策略选错**和**系统没有把选择执行出来**分开看。01、02 局有 109、188 次可点击的阳光落在错误配置的区域外；修好后，03–05 局这类记录是零。04 局还有 753 条收集批次被新批次覆盖的记录；改了队列后，05 局这类记录也是零。[验证记录](../.sdd/006-jev-runtime-loop/verify.md)列出了计算口径。这些是 Harness 的观察和执行问题，不能怪到 JEV 的植物策略上。

## 真正难的是，把下一步接成一段策略

把模型的候选、选择和实际执行放在一起看之后，我对 JEV 的定位更清楚了。它可以很快回答“眼前这些选项，选哪个”，回答也能直接交给程序使用。但一个合法选择，仍可能让已经很强的行继续变强，让缺少火力的行继续空着。**输出有边界，解决的是程序怎样接住判断；整个草坪怎样分配资源，还需要更长的视角。** 这正好对应官方所说的聚焦判断与代码组合。[官方说明](https://docs.typesafe.ai/primitives)。

攒钱就是一个很直观的例子。想种一株更贵的植物，就得允许自己现在先不买便宜的，甚至连续几轮都不买。后来的系统把建设目标保留下来，由代码计算还差多少阳光、哪些余量能花，以及出现什么威胁时要打断等待。这样才有了“为后面几步留资源”的连续行为。**这段连续性来自 Harness 保存目标并执行规则，JEV 仍然负责当下的局部选择。** 在这个项目里，它没有自己建立并持续修正一套长期经营计划。

还有一个容易误会的地方：JEV 能选到什么，取决于系统给它什么。以前建设目标一旦被写成候选过滤条件，其他植物就可能被排除；把这个限制改掉后，可选动作才重新出现。所以看到它总选便宜植物，既要看它的判断，也要看它是不是根本没看到其他选择。Harness 的职责就在这里：把局面整理成合适的问题，让模型的判断有发挥空间，同时让资源和动作遵守整套系统的目标。[候选规则与经济事实](../jev/strategy.py)。

种植和铲除也一样。把它们拆成两个明确的问题，JEV 可以分别判断；但哪一个先执行、是否应该为下一步腾位置，仍要由系统协调。它们不会因为放在一次请求里，就自动成为一个连贯的升级计划。后来的测试进一步支持了我的理解：**JEV 适合成为 Harness 里快速、范围明确的判断环节；把这些判断组织成长线策略，需要目标、记忆、规划和反馈一起工作。** 这也符合官方把局部判断交给模型、把组合逻辑留在代码中的设计。[官方 Primitives](https://docs.typesafe.ai/primitives)。

## 官方其实怎么描述 JEV

TypeSafe 把 JEV 叫作 **System One**：它接收 State，回答预先定义好的问题，返回类型化的选择和概率；目前不直接看图像。官方强调的是快速、聚焦的判断，而不是让它独自完成一整段慢速规划。[System One](https://docs.typesafe.ai/concepts/system-one)。官方也建议把复杂判断拆成小问题，把能精确算的东西留给代码，再由代码组合答案。[Primitives](https://docs.typesafe.ai/primitives)。

这和我们踩到的坑很接近。TypeSafe 自己列出的 `jev-1.13` 弱点包括计数、数字精度、多层间接推断、无关信息过多和互相冲突的说明。[Jev 1.13 jaggedness](https://docs.typesafe.ai/model-jaggedness/jev-1.13)。所以，“给 JEV 更多 State”不能简单理解成把所有游戏数据一股脑塞进去。更有用的是算好相关事实，讲清楚问题，让它判断它真正擅长的不确定部分。

官方提到的低幻觉也要说准：**输出被限制在给定的类型和候选里**，它不会凭空返回一株候选里没有的植物。这保证接口容易接，不保证它在合法候选里选的是最好的行和格子。[Primitives](https://docs.typesafe.ai/primitives)。官方的 Doom 演示同样使用结构化 State，并明确说传统 bot 可能打得更好；一个实时游戏演示不能直接回答 PvZ 的资源经营问题。[官方发布文章](https://typesafe.ai/blog/introducing-system-one-models-and-jev)。

## JEV、LLM、Agent 和 Harness 各做什么

我现在会把它们分开看。**JEV** 回答一个有边界的判断：“眼前这些合法选项，哪一个更合适？”它能跟着新 State 快速重选。**LLM** 可以写出一段解释、提出下一波的打法，或复盘几局共同暴露的问题。**Agent** 是围绕目标不断观察、调用工具、检查结果并调整计划的运行过程，不是一款特定模型。**Harness** 则安排这些能力何时介入：哪些事实可信、哪个问题要问、候选有哪些、动作能否执行、旧决定何时失效、结果怎样留下证据。它们是职责关系，不是一条固定的上下级链。

JevPvz 已有的是代码和 JEV 组成的频繁决策闭环：系统整理状态、保留建设目标、提供候选，再把选择变成可确认的动作。**项目目前还没有接入 LLM/Agent，去自动规划、局后复盘和跨局更新经验。** 官方也把 JEV 放在更大工作流中的聚焦判断位置。[System One](https://docs.typesafe.ai/concepts/system-one)。

如果将来接入 LLM/Agent，我设想的是两个节奏：局面变化快时，代码更新事实、JEV 判断当前的有界选择；到了新波次、重大失误或局后，再让 LLM/Agent 思考一段时间的资源目标和布局，复核实际结果，决定哪些经验值得留下。旧计划还需要版本和失效条件，免得新威胁出现时仍被旧目标拖住。这个分工是**下一步的架构想法**，目前还没有在游戏里实现。同一份 State 上的独立 JEV 问题也不必排成多次请求，官方允许同批回答，再由代码组合。[Primitives](https://docs.typesafe.ai/primitives)。

## 最后怎么下结论

这次至少证明了一件实在的事：**在准备好 State、候选和执行闭环后，JEV 能参与真实游戏并帮助系统通过两个关卡。** 后来的测试进一步让我确认，它适合承担 Harness 中频繁发生的局部判断。长期要建设什么、何时停止投资、怎样调整阵型，不能指望这些下一步选择自然推导出来。

我不会把五局游戏说成 JEV 的“理论上限”。配置每局都在变，没有固定规则或其他模型作同条件对照，也没有把模型、经验和 Harness 的贡献单独测出来。更准确的说法是：**JEV 让 Harness 拥有一个有用的快速判断节点；Harness 决定这个节点看见什么、能做什么、结果是否可信。跨局的规划、复盘和经验更新仍未建成。**
